`0.2.4` 是 `0.2.3` 的增量版本，**没有数据库变更**，接口只新增不破坏。主要做了三件事：上线站内消息中心（含「升级邀请」消息）、装机入口从弹窗改成整页表单、修掉 `0.2.3` 已知限制里列出的首页监控与推广页几个问题。安装包沿用历史 release keystore 签名，可覆盖安装，**不需要卸载**。

## 二、相对 0.2.3 的变化

### 2.1 站内消息中心（新增）

首页与「我的」宫格多了消息入口，点击进入列表 `/messages`，再点开详情 `/messages/:id`：

| 项 | 行为 |
| --- | --- |
| 入口 | 首页铃铛卡片显示未读数红点；「我的」宫格同步显示 |
| 消息内容 | 目前主要是装机申请通知：谁提交的、装的什么机器、当前审核状态 |
| 已读 | 打开详情即已读（后端在详情接口里标记）；列表支持「全部已读」 |
| 空态 | 没有消息时列表显示空态，不请求详情 |

接口（均在 `/message` 下）：`GET /message/list`、`GET /message/unread-count`、`GET /message/:id`、`POST /message/read`、`POST /message/read-all`。

### 2.2 「升级邀请」消息（新增）

列表与详情会把 `type == 'UPGRADE_PROMPT'` 的消息按「升级邀请」样式渲染，标签文案取后端 `typeName`。点击这类消息**不是**跳详情，而是：

1. 先 `GET /team/upgrade-prompt` 实时拉一次最新升级提示；
2. 有数据才弹已有的升级弹窗，弹窗内 `POST /team/upgrade-prompt/choice` 提交 `upgrade` / `decline`；
3. 拉到 `null`（提示已失效，例如已在别处处理过）就不弹空窗，只提示「已失效」并刷新列表。

**与 `0.2.3` 关闭自动弹窗的关系（务必同步清楚）：** `0.2.3` 关掉的是冷启动 / 回前台的**自动**弹窗，这两个场景在 `0.2.4` 仍然静默、仍然不请求接口；从消息里点开是用户主动路径，才会请求 `/team/upgrade-prompt`。两件事互不影响。

### 2.3 装机入口改成整页表单

| 改动 | 要点 |
| --- | --- |
| 「立即装机」弹窗 → 独立页面 | 申请记录点「立即装机」进入整页 `install_apply_page`，底部固定「确认装机」，提交中拦截返回；字段与提交参数和原弹窗一致 |
| 申请页精简 | `apply_machine_page` 不再内嵌装机表单，只负责申请单本身 |
| 「添加机器」新增「商户名称」 | 选填，≤64 字，留空不提交；首页监控卡的门店名即取自此字段 |

### 2.4 首页「机器达标监控」修复

| 问题（`0.2.3` 已知限制里的） | 0.2.4 的修法 |
| --- | --- |
| 只取机器列表第一页 20 台，第 21 台起不出现在监控卡 | 按 `total` 续页把名下机器收齐再渲染 |
| 「全部机器已过期但未达标」时误显示「机器均已达标」 | 空态改多态文案：`未绑定机器` / `机器均已达标` / `达标窗口已结束` |
| 已完成（人工结算）与 `target <= 0` 的历史机器永久占一张「剩余 0 天 / 累计 0 元」卡 | 监控条件加上「未完成」与「有门槛」两个前置，历史机器不再进卡 |

### 2.5 推广中心

- 统计模块隐藏时不再请求 `GET /user/invite/records`（原来每次打开页面和下拉刷新都会白拉 50 条明细）；
- 推广码接口失败时，错误原因与「重试」按钮改为在可见区域展示——原来错误入口和统计模块共用一个开关，隐藏后页面只剩「生成中…」，用户没有任何重试手段。

### 2.6 内部整理（无视觉变化）

- 未读红点抽成共享组件 `UnreadBadge`，首页入口与「我的」宫格共用；
- 达标判定与剩余天数抽成 `ratioReached()` / `reachDaysLeft()`，`Machine` 与新手达标待确认条目共用一份口径，避免两处算法漂移；
- 首页监控卡从一次性铺开改成按需构建。

## 三、自动弹窗的现状（承接 0.2.3）

两个自动弹窗在 `0.2.4` 仍默认关闭（`appRouter` / `ShellLayout` 的 `enableDialogs`，默认 `false`）：

| 弹窗 | 0.2.4 行为 |
| --- | --- |
| 升级提示（冷启动 / 回前台） | 不弹，也不请求 `/team/upgrade-prompt` |
| 机器达标双方确认 | 不弹，也不请求 `/pos/newbie/confirmations` |

组件、接口封装与后端逻辑全部保留；需要恢复时把 `enableDialogs` 默认值改回 `true`。升级邀请消息的「点击 → 拉取 → 弹窗」链路不受这个开关影响。

## 四、服务端配套

- `/message` 系列接口（`super-sales-server` 的 `src/modules/app/message`）需已部署，否则首页消息入口与「我的」宫格红点保持 0；
- 升级提示两个接口（`GET /team/upgrade-prompt`、`POST /team/upgrade-prompt/choice`）与新手达标两个接口（`GET /pos/newbie/confirmations`、`POST /pos/newbie/confirm`）继续可用；
- 机器列表出参需包含 `merchantName` / `installedAt` / `dueAt` / `windowDays` / `taskSelfPoints`，缺字段时监控卡降级显示机型与默认规则；
- 本版本**没有**新增数据库变更；`0.2.3` 提到的 `pos_newbie_confirm` 表与迁移仍按原计划执行。

## 六、升级与发布注意

- 安装包为 release 签名，与 `0.1.9` 及 `0.2.1`～`0.2.3` 一致，可直接覆盖升级；
- **后台版本记录要改成 `0.2.4` / versionCode `15`**，下载地址指向 `https://zhy-h5.citykafei.com/download/kqw-0.2.4.apk`；不改的话 App 冷启动的更新提示只会推到旧版本；
- release 包默认连生产 `https://zhy-api.citykafei.com`，不含内网明文 HTTP 放行，也不要加 `--dart-define` 覆盖后端地址；
- `--debug` 包与 release 包签名不同，手机上一旦装过 debug 包，必须先卸载才能装正式包（卸载会清本地登录态，需重新用手机号验证码登录）。

## 七、已知限制

- 站内消息完全依赖后端 `/message` 接口，后端未部署时入口存在但永远是空列表；
- 升级邀请消息点开时才拉最新提示，若提示已被其他端处理，会提示失效并刷新列表，需要用户重新进消息；
- 监控卡的门店名依赖机器列表的 `merchantName`，自装机器和早期没有该字段的机器显示机型；
- 已达标且窗口已过的机器不列入首页监控（`0.2.3` 起的既定口径）；
- 两个自动弹窗仍关闭，因此冻结奖励只能等 30 天到期兜底转推荐人，机器达标只能走后台人工审核——这两条业务影响与 `0.2.3` 相同，没有变化。
